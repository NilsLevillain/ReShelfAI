# Reshelf: War Plan

Execution strategy for building Reshelf, a portfolio grade SaaS demo that allocates bad stock to second life channels. It complements the product brief and explains how we build, in what order, and how we know each step works.

Status: approved direction, no code yet. Time budget: about 8 weeks, part time.

---

## 0. Verdict in one screen

| Topic | Decision |
|---|---|
| Hero story | "Tighten a rule, see what it costs, and see why." Scenario compare plus the "Why this allocation" panel are the product. |
| Visual hook | 3D globe on the stock overview. It opens the video and the app. |
| Explainability | Feasible in scope: rule trace plus on demand counterfactual re solves. No MILP duals in v1 (see section 5.6). |
| Hosting | Static frontend with precomputed results, optional live API. Always instant, even on a cold free tier. |
| Scope | 8 weeks covers the MVP. Second wave goes to the roadmap, except "parameter impact", which comes for free with scenario compare. |
| Name | Reshelf (working name, recommended). |

## 1. Clean room principles (week 0, before any code)

* Fresh repository with a fresh `git init`. No history imported from anywhere.
* All data is synthetic and generated by a seeded script.
* Every rule value is invented and documented as an illustrative default.
* Only generic, public ERP concepts and standard SAP table and field names.
* Visual design made from scratch. Page flow: home cards, KPI tiles, stock inflow and outflow waterfall, material deep dive.
* KPIs are simulated and always shown against a greedy baseline on synthetic data. No claim of real business impact.

## 4. Data model (ERP portable)

### 4.1 Layers

```
Source tables (SAP style CSV / Parquet / warehouse)
        │  SourceAdapter (Protocol)
        ▼
Canonical dataset (Pydantic + pandera validated)
        │
        ▼
Solver input (lots, channels, rules, demand, scores)
```

The solver never sees raw ERP tables.

### 4.2 Source tables

Standard: `MARA`, `MAKT`, `MARC`, `MARD`, `MCHB` (with `VFDAT`, `HSDAT`), `MBEW`, `T001W`, `T023`.
Custom: `ZCHANNEL`, `ZCHANNEL_RULE`, `ZSELLIN`, `ZSELLOUT`, `ZABC`, `ZPARAM`.

### 4.3 Adapter

```python
class SourceAdapter(Protocol):
    def load(self) -> CanonicalDataset: ...
```

* v1: `CsvAdapter`, `ParquetAdapter`.
* v1 stub plus ADR: `BigQueryAdapter` (interface and SQL views documented, not wired).

### 4.4 Canonical entities

| Entity | Key fields |
|---|---|
| `Lot` | `material`, `plant`, `expiry_date`, `qty`, `unit_cost` |
| `Material` | `material`, `description`, `category`, `brand`, `tier`, `shelf_life_months` |
| `Channel` | `channel`, `type`, `country`, `lat`, `lon`, `capacity_units`, `max_skus` |
| `ChannelRule` | `channel`, `min_rsl_pct`, `allowed_tiers`, `recovery_factor`, `brand_penalty` |
| `Demand` | `material`, `channel`, `daily_demand`, `seasonality`, `channel_stock` |
| `Abc` | `material`, `abc_class`, `rank` |

**Key decision (ADR 003):** the decision index is the **lot** (material × plant × expiry bucket), not the material × plant pair. Remaining shelf life rules stay exact without per batch variables, and the model size stays controlled by bucketing expiry by month.

### 4.5 Deliverables

* `docs/erd.md`: Mermaid ERD of source and canonical layers.
* `docs/mapping.md`: field level mapping, source table.field → canonical field → transformation.
* `data/generator`: seeded generator with aging curves, ABC Pareto skew, seasonality, brand tier mix. Tests assert the distributions (share of A class, aging histogram shape, tier mix).

## 5. Optimization model

### 5.1 Solver stack

* PuLP behind a `Solver` protocol (`solve(model_input, params) -> SolveResult`).
* HiGHS (`highspy`) default, CBC fallback.
* `SolveResult` always carries `status`, `objective`, `mip_gap`, `time_s`, `time_limit_s`. The API returns them as is.

### 5.2 Notation

| Symbol | Meaning |
|---|---|
| L, C, M | lots, channels, materials |
| m(l), t(l) | material and brand tier of lot l |
| A ⊆ L × C | admissible pairs after elimination (shelf life, tier) |
| G | assortment groups (category × brand) |
| q_l, v_l | available units and unit cost of lot l |
| r_c, β_{c,t} | recovery factor of channel c, brand penalty per unit of tier t in c |
| K_c, S_c, A_{g,c} | capacity units, max SKUs, max SKUs of group g in channel c |
| D_{m,c} | coverage need: max(0, demand × coverage days × seasonality − channel stock) |
| P_{m,c} | push quantity for NEW materials |
| w_m | material score |

Variables: x_{l,c} ∈ ℤ≥0, y_{l,c} ∈ {0,1}, z_{m,c} ∈ {0,1}, defined only for (l,c) ∈ A.

### 5.3 Elimination before modeling

A pair (l,c) is dropped from A when:

* remaining shelf life at delivery < `min_rsl_pct` of channel c, or
* tier t(l) is not in `allowed_tiers` of channel c (for example luxury and premium are not allowed in donation or clearance).

This is faster and easier to explain than constraints. Each dropped pair keeps a reason code for the Why panel.

### 5.4 Constraints

| # | Name | Formulation |
|---|---|---|
| 1 | `supply[l]` | Σ_c x_{l,c} ≤ q_l |
| 2 | `link_xy[l,c]` | x_{l,c} ≤ q_l · y_{l,c} |
| 3 | `link_yz[l,c]` | y_{l,c} ≤ z_{m(l),c} |
| 4 | `link_zy[m,c]` | z_{m,c} ≤ Σ_{l ∈ L(m)} y_{l,c} |
| 5 | `cap[c]` | Σ_l x_{l,c} ≤ K_c |
| 6 | `sku[c]` | Σ_m z_{m,c} ≤ S_c |
| 7 | `asrt[g,c]` | Σ_{m ∈ g} z_{m,c} ≤ A_{g,c} |
| 8 | `cov_hi[m,c]` | Σ_{l ∈ L(m)} x_{l,c} ≤ D_{m,c} · z_{m,c} |
| 9 | `cov_lo[m,c]` | Σ_{l ∈ L(m)} x_{l,c} ≥ α · min(D_{m,c}, Q_m) · z_{m,c} |
| 10 | `push[m,c]` | Σ_{l ∈ L(m)} x_{l,c} ≥ min(P_{m,c}, Q_m) · z_{m,c}, for NEW m |

Q_m is the total available units of material m. Constraints 8 to 10 are the tight form of the Big M formulation: the binary multiplies the smallest valid bound directly, so the coverage and push rules apply only when the SKU is selected. Where a Big M is unavoidable, M is the tightest available bound, never a generic constant. ADR 004 documents this.

### 5.5 Objective (two phase lexicographic)

* **Phase 1:** S* = max Σ_{m,c} w_m · z_{m,c}
* **Phase 2:** add Σ w_m · z_{m,c} ≥ (1 − ε) · S*, then
  max Σ_{(l,c) ∈ A} (v_l · r_c − β_{c,t(l)}) · x_{l,c}

ε defaults to 1% to avoid numerical deadlock and leave room for value. Units not allocated count as destroyed.

**Illustrative score (invented default, stored in `ZPARAM`, never in code):**

w_m = base[class] + 0.25 · (1 − rank_m / N)

| Class | base |
|---|---|
| A | 1.00 |
| B | 0.70 |
| C | 0.40 |
| NEW | 0.55 |

### 5.6 Explainability: recommendation

| Option | Upside | Downside | Decision |
|---|---|---|---|
| Duals after fixing integers and re solving the LP | Classic OR answer | Only valid locally, often degenerate, hard to explain to planners | Rejected for v1, ADR notes it as a later "advanced" toggle |
| **Rule trace + on demand counterfactual** | Exact, readable, testable, in euros | Counterfactual costs one re solve per click | **Chosen** |

How it works:

1. **Rule trace (instant).** After the solve, read the slack of every named constraint. A constraint is binding when slack ≤ tolerance. Each allocation line (l,c) lists the binding constraints it appears in, plus the elimination reasons that blocked other channels.
2. **Counterfactual (on click).** From the Why panel, relax one binding rule (+10% or off), warm start from the current solution, re solve phase 2 with a 10 s limit, and report "this rule costs X € on total value, Y units more destroyed".
3. **Precompute** the counterfactuals for the top binding rules of each seeded scenario in CI, so the static demo shows them without a backend.

### 5.7 Greedy baseline

Sort lots by value at risk (units × cost × urgency). Assign each lot to the admissible channel with the best recovery factor that still has capacity. It uses the same constraint checker as the optimizer, so the comparison is fair.

### 5.8 KPIs per scenario

Value recovered, units destroyed, brand risk index (Σ β·x / Σ v·x), SKUs selected per channel, channel fill rate, solver status and gap.

### 5.9 Tests and benchmark

* One pytest per constraint (feasible and violating cases), infeasible scenario, empty input, single channel, all lots eliminated.
* Property test: optimizer value ≥ greedy value on any seeded dataset.
* Benchmark matrix in `docs/benchmark.md`: 300 / 2,000 / 10,000 SKUs × 5 / 20 channels, with HiGHS and CBC, time and gap.

## 6. Architecture

### 6.1 Stack

| Layer | Choice |
|---|---|
| API | Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic, SQLite (Postgres ready) |
| Solver | PuLP, HiGHS, CBC |
| Web | React, TypeScript, Vite, Tailwind, shadcn/ui, TanStack Table (virtualized), TanStack Query, Recharts |
| Globe | `react-globe.gl`, lazy loaded |
| Export | openpyxl, generic order creation format |
| Auth | Mocked roles: planner, viewer, admin |

### 6.2 API surface (first draft)

| Method | Path | Purpose |
|---|---|---|
| GET | `/stock/summary` | KPI tiles, aging buckets, value at risk |
| GET | `/stock/lots` | stock health table (filters, paging) |
| POST | `/scenarios` | create a scenario from parameters |
| POST | `/scenarios/{id}/solve` | run optimizer and baseline |
| GET | `/scenarios/{id}/results` | allocation lines and KPIs |
| GET | `/scenarios/compare?ids=` | KPI deltas between scenarios |
| GET | `/results/{id}/lines/{line}/explain` | rule trace |
| POST | `/results/{id}/lines/{line}/counterfactual` | relax one rule and re solve |
| GET | `/scenarios/{id}/export.xlsx` | Excel export |

### 6.3 Pages

Home → Stock overview (globe + stock health table) → Parameters → Results (table + charts + Why panel) → Compare → Material deep dive.

### 6.4 Globe

* Points sized by value at risk per plant, arcs plant → channel after a solve.
* Click a plant or country → stock table filtered on it. The globe itself is quick to build; the real work is the drilldown filter wiring.
* Lazy loaded chunk, table fallback when WebGL is missing or on small screens.

### 6.5 Demo mode

* `make precompute` runs the real solver on each seeded scenario and writes `data/precomputed/*.json` (results, KPIs, rule traces, top counterfactuals). CI runs it on each release.
* The frontend reads precomputed JSON by default (Vercel or GitHub Pages).
* If `VITE_API_URL` answers a health check, it switches to live mode.
* A banner always shows "Cached results" or "Live solver".
* API on Cloud Run, scaled to zero. Render is the fallback.

### 6.6 Built for the video

Stable `data-testid` on every hero element, deterministic seeds, fixed demo scenario, no random animation timing.

## 11. Risks and assumptions

| Risk | Impact | Mitigation |
|---|---|---|
| Seeded story too flat (optimizer barely beats greedy) | Weak demo and video | Tune generator in week 1, assert a minimum gap in a test |
| Solve time on free tier | Slow live demo | Precomputed JSON, time limits, gap reported |
| Counterfactual re solve too slow at scale | Laggy Why panel | Warm start, 10 s limit, precompute top rules |
| Scope creep into second wave | Missed video deadline | Weekly "not built" column, cut order above |
| Globe performance on low end laptops | Bad first impression | Lazy load, table fallback |
| Remotion learning curve | Late video | Storyboard locked in week 6, hybrid approach |

Assumptions: HiGHS solves the 2,000 SKU demo in seconds; free tiers stay available; reviewers value tests and ADRs as much as visuals.
